## Requirement understanding

One line: Add a tool to the Ingram Micro MCP connector that lists a customer's Ingram Micro Cloud Marketplace subscriptions (to find which M365-type subscriptions need a license added or removed), because the connector currently only wraps the Ingram Micro Resellers API and has no coverage of the separate IM Cloud / CloudBlue Marketplace API.

Restatement: this is gap #27 from the Rewst → MSPbots migration gap register, for the Rewst account "Ginko IT". Two of Ginko's Rewst flows (`M365 Licensing: Ingram Micro: Purchase License`, 170 runs/year; `Remove License`, 110 runs/year) call a Rewst action `im_cloud.list_subscriptions` to look up a customer's active cloud subscriptions before adding/removing seats. MSPbots' `ingrammicro-mcp` has 24 tools, all of them wrapping the Ingram Micro **Resellers** REST API (`/resellers/v6`, `/resellers/v7`); none of them call the IM Cloud / CloudBlue Marketplace subscription object. Success is: an agent can call one new tool with a customer id and get back that customer's subscriptions (id, plan, status, products, renewal date, price) the same way the Rewst action does today.

## Current state

- `MSPbotsAIFramework/ingrammicro-mcp@main` (4171891) has 24 tools across 8 modules (`tools/catalog.py`, `orders.py`, `quotes.py`, `invoices.py`, `renewals.py`, `deals.py`, `returns.py`, `freight.py`), all calling `/resellers/v6*` or `/resellers/v7*` — confirmed by grepping every `client.get/post/put/delete(` call site and the README's own tool table (README.md:184-254). No module, client, or config entry references the IM Cloud / CloudBlue Marketplace API.
- `src/ingrammicro_mcp/api_client.py` (`IngramMicroClient`) implements exactly one auth scheme: OAuth2 `client_credentials` via `GET {base_url}/oauth/oauth20/token` with `client_id`/`client_secret` as **query params** (api_client.py:163-172), re-authenticating on every call (no token cache), plus three business headers (`IM-CustomerNumber`, `IM-CountryCode`, `IM-CorrelationID`) and an optional `IM-SenderID`/`IM-ApplicationID` pair (api_client.py:174-195). This is the Ingram **Resellers** API's documented auth shape, not a generic Ingram Micro auth layer.
- `src/ingrammicro_mcp/config.py` defines one credential set (`ingrammicro_client_id/_secret/_customer_number/_country_code`) and one base URL (`ingrammicro_base_url`, default `https://api.ingrammicro.com`), with `gateway`/`env` auth modes (config.py:17-44).
- `src/ingrammicro_mcp/server.py` reads the four `X-IngramMicro-*` headers into a per-request `contextvar` in `GatewayTokenMiddleware` (server.py:52-99) and builds one `IngramMicroClient` per request via `client_factory` (server.py:108-110). Tool modules only ever see `client_factory()` — they never touch headers or config directly (e.g. `tools/renewals.py:21-80`).
- The ticket's own evidence (`text_content`) states the local reference build at `D:\html\ingrammicro-mcp` has the same 24-tool, Resellers-only coverage — consistent with what's in `main`.

**Wiki**: not covered. `mbp.py wiki find "Ingram Micro" / "IM Cloud" / "ingrammicro"` returned no hits in `MSPbotsAI/mbagent-wiki` ProductDocs (synced 2026-10-30, HEAD feccb34). There is no existing product-fact page for this connector to check against or update yet; the connector-wiki step (owned by the review leg per `mcp-track.md` 4.5) will be the first page for this connector.

**External API facts** (the IM Cloud API is not this repo's own API, so "current state" for it means "what is publicly documented", not code):
- Ingram Micro's Xvantage platform publishes a "Cloud Marketplace API" (PDF: `developer.ingrammicro.com/sites/default/files/2025-11/Cloud%20Marketplace%20API.pdf`) and a dedicated docs site `apidocs.cloud.im/1.15/` ("Cloud Marketplace API - Ingram Micro Cloud"). Both are publicly linked from Ingram's own developer portal (found via web search, not behind a login wall as far as the search results show); the pipeline's network access could not reach either URL directly from this environment (`ECONNRESET` / timeout on `WebFetch`, no response via `curl`), so the exact base URL, auth header names, and full response schema from Ingram's **own** copy of this spec are not verified in this pass — see Risks.
- Ingram's Xvantage integration layer is itself built on **CloudBlue Connect** (per the GitHub org name `ingrammicro-xvantage` and CloudBlue's own community docs describing the same "Marketplace API" and "Subscriptions" module). CloudBlue's generic Simple API docs (`docs.cloudblue.com/cbc/21.0/Simple-API/how-to-use/howto/subscriptions/`, fetched directly) document exactly the endpoint shape the ticket describes:
  - `GET /subscriptions?customerId={id}&status={status}` — `customerId` = "the ID of the subscriber", `status` one of `pending|active|hold|terminated|removed`.
  - Auth: `Authorization: Bearer {token}` plus an `X-Subscription-Key: {key}` header.
  - Response: list of subscription objects — `id`, `customerId`, `status`, `renewalStatus`, `creationDate`, `renewalDate`, `lastModifiedDate`, `totalPrice` (`{currency, amount}`), `products[]` (`mpn`, `quantity`, `unitPrice`, `extendedPrice`), plus pagination (`offset`/`limit`/`total`).
  - This matches the ticket's own field list (`id, name, planId, status, customerId, products[] (mpn, name, quantity, unitPrice), renewalDate, totalPrice`) closely enough (the ticket additionally expects `name` and `planId` at the subscription level, which Ingram's own branded deployment plausibly adds — unverified) to treat the CloudBlue shape as the reliable baseline contract, with Ingram-specific field names to be confirmed against the two Ingram-hosted documents above during implementation.

## Product design

### Goals / Non-goals

**Goals**
- Add one new tool, `ingrammicro_cloud_list_subscriptions`, that lists a customer's Ingram Micro Cloud Marketplace subscriptions, filterable by status and creation-date range, so an agent can find the subscription to add/remove seats on before calling a (future, out of scope) seat-change tool.
- Match the Rewst action this replaces (`im_cloud.list_subscriptions`) closely enough that the two Ginko IT flows named in the gap register (`Purchase License`, `Remove License`) can be rebuilt against this tool with the same inputs and the fields they need (`id`, `planId`, `status`, `customerId`, `products[]`, `renewalDate`, `totalPrice`).

**Non-goals** (not this ticket)
- Placing, modifying, or cancelling a Cloud Marketplace subscription or order — the gap register entry is read-only ("找到要加减许可的 M365 订阅"); the actual add/remove-seat action is a separate capability, not named in this gap, and not designed here.
- Any other IM Cloud / CloudBlue Marketplace object (products, listings, orders) beyond subscriptions.
- Changing anything about the existing Resellers-API tools.

### Acceptance criteria

- **AC1** — Given valid Cloud Marketplace credentials and a `customerId` with at least one subscription, When `ingrammicro_cloud_list_subscriptions` is called with `status="active"`, Then the response is a JSON list where each item has `id`, `status`, `customerId`, `renewalDate`, `totalPrice`, and `products[]` (each with `mpn`, `quantity`, `unitPrice`), and only subscriptions in `active` status are present.
- **AC2** — Given the same account, When called with no `status` filter, Then subscriptions in any status are returned (server does not filter) and the tool does not silently default to `active`.
- **AC3** — Given a `customerId` with zero subscriptions, When the tool is called, Then the response is an empty list, not an error.
- **AC4** — Given `creationDateFrom`/`creationDateTo` are supplied, When the tool is called, Then only subscriptions created in that window are returned.
- **AC5** — Given the Cloud Marketplace credential headers are missing or incomplete, When any tool in this module is called, Then the response is a structured `not_configured` error (same shape as the existing `NO_TOKEN` envelope for the Resellers tools) naming the missing header(s), and no request reaches Ingram Micro.
- **AC6** — Given Ingram's Cloud Marketplace API returns an error (4xx/5xx, or a network failure), When the tool is called, Then the response is a structured error envelope (`error_envelope`, same shape the Resellers tools already use) with a code, message, and `retryable` flag — never an unhandled exception or a raw stack trace.
- **AC7 (multi-tenant / BOLA)** — Given two different connected organizations (tenants) each with their own Ingram Micro Cloud account, When one organization's agent calls this tool, Then it can only ever see that organization's own `customerId` — `customerId` is bound to the gateway credential for that connection, not an agent-suppliable call argument, so there is no way for a prompt or a malicious instruction to make one tenant's agent list another tenant's subscriptions by passing a different id. (See Tech design → Decision 1 for why this differs from the gap register's literal field list.)

### Open questions

- **Q1 — exact base URL and header names for Ingram's own IM Cloud API deployment.** Not resolved in this pass (see Current state → External API facts and Risks). **Not blocking**: dev builds against the documented CloudBlue Simple API contract (verified facts above) behind a client wrapper whose public method (`CloudMarketplaceClient.list_subscriptions(...)`) does not change if the exact header names differ — only the client's internal header names and `_login()`/base URL need adjusting once dev opens the two Ingram-hosted PDFs/doc sites (network access may differ per machine) or gets a real Cloud Marketplace account. Flagged in Risks, not Open-question-blocking.
- **Q2 — does the IM Cloud API need an OAuth2 token exchange (like the Resellers API) or is the API key used directly as the Bearer token?** CloudBlue's generic docs only show `Authorization: Bearer {token}` with no visible exchange step; assumed to be a direct API key for this design (Decision 2 below). Not blocking — same reasoning as Q1: the wrapper boundary absorbs this either way.

## Tech design

### Conclusion

Add a new, self-contained module for the Cloud Marketplace API — new client, new tool file, new credential headers and config — without touching any of the 24 existing Resellers-API tools or `IngramMicroClient`. The two APIs have different auth schemes, different base URLs, and different credential material, so they get separate client classes; the shared HTTP-with-retry plumbing is extracted into a small shared module so the new client reuses it instead of duplicating it (see Reuse & cleanup).

### Where the current implementation lives

- `src/ingrammicro_mcp/api_client.py` — `IngramMicroClient` (Resellers API only); `_request_with_retry`/`_get_http_client`/retry constants (lines 1-40, 93-135) are generic HTTP-client plumbing with nothing Resellers-specific in them.
- `src/ingrammicro_mcp/config.py` — `Settings` (pydantic-settings), one credential set, one base URL, `auth_mode` gateway/env switch.
- `src/ingrammicro_mcp/server.py` — `GatewayTokenMiddleware` reads headers into a contextvar; `get_client_from_context` builds the client; `create_mcp_server` registers each tool module via `<module>.register(mcp, client_factory)`.
- `src/ingrammicro_mcp/tools/_common.py` — shared `NO_TOKEN` envelope constant.
- `src/ingrammicro_mcp/tools/renewals.py` — closest existing pattern for a read-only "search with optional filters" tool (used as the template for the new tool's shape).

### Option analysis

1. **Add Cloud Marketplace support to the existing `IngramMicroClient`/`Settings`** (one client, one credential set with extra optional fields) — rejected. The two APIs have unrelated auth (OAuth2 query-param client_credentials vs. a Cloud Marketplace API key + `X-Subscription-Key`), different base URLs, and are logically different vendor products (Resellers vs. Cloud Marketplace); folding them into one class would make `has_credentials`/`_login()` branch on "which API is this call for", which is more special-casing than a second small client.
2. **New client, new tool module, new credential headers, shared HTTP plumbing extracted into a small shared module** (chosen) — mirrors how this repo already separates concerns (one client = one upstream API, one tool module per capability area) and keeps the blast radius of "IM Cloud API details are unverified" (Q1/Q2) contained to one new file.
3. **Build the tool directly against `httpx` with no client wrapper class** — rejected, inconsistent with every other tool in this repo and would duplicate the retry/error-envelope logic `IngramMicroClient` already has.

- **Change** `src/ingrammicro_mcp/api_client.py` — import the extracted helpers from `_http.py` instead of defining them locally; `IngramMicroClient` itself (the Resellers-specific `_login`, `_business_headers`, `get/post/put/delete`) is unchanged.

### Data & API contract

**New tool**

```
ingrammicro_cloud_list_subscriptions(
    status: str | None = None,              # "pending" | "active" | "hold" | "terminated" | "removed"
    creation_date_from: str | None = None,   # ISO 8601 date
    creation_date_to: str | None = None,     # ISO 8601 date
) -> str   # JSON-encoded list, via dump_json_capped — same as every other tool in this repo
```

`customerId` is **not** a tool parameter (Decision 1) — it comes from the `X-IngramMicroCloud-Customer-Id` gateway header, exactly like `IM-CustomerNumber` already does for the Resellers tools.

**Upstream call** (per the verified CloudBlue Simple API contract, pending the two confirmations in Risks):

```
GET {ingrammicro_cloud_base_url}/subscriptions?customerId={header value}&status={status}&creationDateFrom={..}&creationDateTo={..}
Authorization: Bearer {X-IngramMicroCloud-Api-Key}
```

Response (per CloudBlue docs; Ingram's own deployment may add `name`/`planId` per the ticket's field list — to be confirmed, not a breaking assumption either way since this tool just passes the response through):

```json
[
  {
    "id": "...", "customerId": "...", "status": "active",
    "renewalDate": "...", "totalPrice": {"currency": "USD", "amount": 0},
    "products": [{"mpn": "...", "quantity": 0, "unitPrice": 0}]
  }
]
```

**Error envelope** (unchanged shape, reused from `_json.error_envelope`):

```json
{"error": {"code": "not_configured|unauthorized|not_found|invalid_argument|rate_limited|upstream_error", "message": "...", "retryable": false}}
```

**Backward compatibility**: fully additive. No existing header, tool signature, or response shape changes. A gateway/client that never sends the two new headers sees no behavior change in any existing tool.

### Key flow / sequence

1. Agent calls `ingrammicro_cloud_list_subscriptions(status="active")`.
2. `GatewayTokenMiddleware` has already read `X-IngramMicroCloud-Api-Key` / `X-IngramMicroCloud-Customer-Id` from the request into the Cloud contextvar (if present).
3. `tools/cloud.py` calls `cloud_client_factory()`. If `None` (headers missing) → return `NO_CLOUD_TOKEN`, no upstream call (AC5).
4. `CloudMarketplaceClient.list_subscriptions(status=...)` builds `GET /subscriptions?customerId=<from credential>&status=active`, sends `Authorization: Bearer <api key>`, via the shared `_request_with_retry`.
5. Success → `dump_json_capped(result)` returned as-is (AC1-AC4). Upstream error → `IngramMicroError.to_envelope()` (AC6).

### Non-functional

- **Multi-tenant isolation**: `customerId` is credential-bound, not agent-suppliable (AC7/Decision 1) — this is the one place this design actively diverges from the gap register's literal parameter list, for a tenant-isolation reason.
- **Statelessness / concurrency**: `CloudMarketplaceClient` takes no shared state (api_key/customer_id passed at construction, built fresh per request via `cloud_client_factory`, same pattern as `IngramMicroClient`); the shared `httpx.AsyncClient` connection pool in `_http.py` carries no credentials, matching the existing comment in `api_client.py` about why sharing the pool across tenants is safe.
- **Credentials**: never logged, never cached beyond the single request's contextvar lifetime — same as the existing four Resellers headers.
- **Performance**: single upstream GET per call, same retry/backoff policy (3 retries, exponential backoff capped at 20s, honors `Retry-After`) as every other tool in this repo — no new performance characteristic.
- **Observability**: no new logging added; this repo has no existing per-tool logging to extend (consistent with current state, not a gap introduced by this ticket).

### Rollout & rollback

- Purely additive — ships as part of the next INT publish of `ingrammicro-mcp`'s default branch. No migration, no existing-tool behavior change, no feature flag needed: a gateway that doesn't send the two new headers never exercises the new code path beyond `cloud_client_factory()` returning `None`.
- Rollback = revert the merge commit; no data or schema to roll back (no database in this repo).

### Test strategy

- **Automated** (`tests/test_cloud_tools.py`, mocking `CloudMarketplaceClient`, following `tests/test_tools.py`'s existing pattern): happy path with `status` filter, no-filter call, empty-list response, missing-credentials envelope (AC5), upstream-error envelope (AC6), date-range filter passthrough (AC4).
- **Manual, needs a real Ingram Micro Cloud Marketplace account** (not available — does not block this ticket per the vendor-mcp "no test account is not a blocker" rule): AC1 and AC2 against a live account with real subscriptions, to confirm the exact response field names (`name`/`planId`) and the real base URL/auth exchange (Q1/Q2).
- **Security**: AC7 is testable without a real account — a unit test asserting the tool signature has no `customer_id`/`customerId` parameter and that `CloudMarketplaceClient.list_subscriptions` always sources `customerId` from `self._customer_id`, never from a call argument.

### Effort & breakdown

Small — one new client (~60 lines, closely mirrors `IngramMicroClient`), one new tool file (~40 lines, mirrors `renewals.py`), one small refactor (`_http.py` extraction), config/middleware wiring, README update, unit tests. Rough estimate: 0.5-1 dev day, no sub-ticket split needed.

### Risks & dependencies

- **Risk**: Ingram's own IM Cloud API deployment may use different header names, a different base URL, or an OAuth2 exchange step instead of a direct API key (Q1/Q2). Mitigated by the client-wrapper boundary (only `cloud_api_client.py`'s internals would need to change, not the tool signature or any other file) and by building against the independently-verified CloudBlue Simple API contract rather than guessing. Dev should fetch `https://developer.ingrammicro.com/sites/default/files/2025-11/Cloud%20Marketplace%20API.pdf` and `https://apidocs.cloud.im/1.15/` before finalizing `cloud_api_client.py` (this design's environment could not reach either URL — `ECONNRESET`/timeout — a dev machine with different network access may succeed where this one didn't).
- **Risk**: the ticket's field list includes `name` and `planId` at the subscription level, not present in the generic CloudBlue docs fetched for this design — likely an Ingram-specific addition to the response schema. Not blocking: the tool passes the upstream response through as-is (`dump_json_capped(result)`), so extra fields surface automatically once a real account is available to confirm them; nothing in this design assumes a fixed, hand-typed schema that would need changing.
- **Dependency**: none on other tickets. This is a self-contained addition to one existing MCP repo.
- **Release order**: `vendor-mcp`, single repo — no cross-repo sequencing needed (see `Track:` line in the ClickUp stub).
