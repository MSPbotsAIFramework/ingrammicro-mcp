## Requirement understanding

One line: Add a tool to the ingrammicro-mcp connector that fetches an Ingram Micro Cloud subscription's details (billing period, subscription period, product lines with mpn/quantity) by subscription id, so the data a Rewst flow currently gets from im_cloud.get_subscription before placing a quantity-change order is available to the Agent platform.

Sources: ticket text_content (gap-register item 28, Rewst account "Ginko IT", verified 2026-10-28); code at `MSPbotsAIFramework/ingrammicro-mcp@main` (4171891); wiki checked via `mbp.py wiki find` for "Ingram Micro" / "Ingram Micro Cloud" / "ingrammicro" — **wiki not covered** (ProductDocs has no entry for this connector; this is a backend MCP tool, not a MSPbots product UI surface, so no `_verified_` user-facing fact applies here anyway).

The ticket is a 1:1 translation of one row in `mspbots-gap-register.xlsx` (the Rewst → MSPbots migration gap list): Rewst's `im_cloud.get_subscription` action calls `GET {IM Cloud API}/subscriptions/{id}` and the flow uses the result's `billingPeriod`, `subscriptionPeriod`, and `products[].mpn` / `quantity` before placing a subscription quantity-change order. The ticket does not ask for the order-placement half of that flow — only the read.

## Current state

`MSPbotsAIFramework/ingrammicro-mcp@main` (4171891) is a single connector with 24 tools, all wrapping **Ingram Micro's Reseller API** (`IngramMicroClient` in `src/ingrammicro_mcp/api_client.py`, base URL `https://api.ingrammicro.com`, OAuth2 client_credentials via `GET /oauth/oauth20/token` with four gateway headers `X-IngramMicro-Client-Id/-Client-Secret/-Customer-Number/-Country-Code`, see `server.py:20-103`). The Reseller API's own OpenAPI spec (`github.com/ingrammicro-xvantage/xi-sdk-openapispec`, `openapispec/unified/XI-Resellers-API-Spec.json`, re-fetched 2026-10-30) has no `/subscriptions/{id}` path — grepping the spec for `subscription` only turns up catalog query-string examples (`type=IM::subscription`), confirming the ticket's own "现状与依据" line: the existing 24 tools cannot serve this request, there is no partial coverage to extend.

`GET {IM Cloud API}/subscriptions/{id}` is **not** the Reseller API under a different path — it belongs to a separate Ingram Micro product, the **Cloud Marketplace API** (built on the CloudBlue Connect platform; Ingram Micro's own branding is "IM Cloud" / "Ingram Micro Cloud", the same name the gap-register row uses). Verified independently (not from the ticket's say-so):

- Public docs exist and are not behind a login wall: `developer.ingrammicro.com/reseller/cloud-api-documentation` (landing page, links an OpenAPI spec + PDF guide) and the API's own hosted reference at `apidocs.cloud.im` (`/1.9/howto/subscriptions/`, `/1.9/howto/ready/`).
- `GET /subscriptions/{id}` is a real, documented endpoint on that API (`apidocs.cloud.im/1.9/howto/subscriptions/`: "To view details of a certain subscription... `GET /subscriptions/1000177`"); a companion list endpoint `GET /subscriptions?customerId=...&status=...` also exists but is out of scope here (not asked for).
- **Base URL is tenant/region-specific**, not a single fixed host: `https://api.cloud.im/marketplace/<region>` (`na` / `eu` / `stg` seen in public integration guides), found in the reseller's own Cloud Marketplace control panel URL. This cannot be hardcoded for "Ginko IT" or any other tenant.
- **Auth is a different scheme from the Reseller API**: `POST /token` with HTTP Basic (`Authorization: Basic base64(username:password)`) plus a required `X-Subscription-Key` header returns a bearer token; subsequent calls send `Authorization: Bearer <token>` + the same `X-Subscription-Key` header; an optional `X-Client-Id` header identifies the calling integration. This is unrelated to the Reseller API's `client_id`/`client_secret`/`customer_number`/`country_code` — none of those four values authenticate against the Cloud Marketplace API.
- `billingPeriod`/`subscriptionPeriod` as `{type, duration}` objects (matching the ticket's field list) are documented on the sibling Products/Orders pages of the same API family, consistent with the ticket's return-field list.

Net: this is not "add one more tool that calls the existing client with a new path" — it requires a second, independently-credentialed HTTP client inside the same connector, because the two APIs do not share a base URL, an auth scheme, or a credential set.

## Product design

### Goals / Non-goals

**Goals**
- Add exactly one new tool, `ingrammicro_cloud_get_subscription`, that fetches one Cloud Marketplace subscription by id and returns `id`, `name`, `planId`, `status`, `products[]` (`mpn`, `name`, `quantity`, `unitPrice`, `currency`), `billingPeriod{type,duration}`, `subscriptionPeriod{type,duration}`, `renewalDate`, `customerId` — the exact field list the ticket and the Rewst flow need.
- Credentials for the Cloud Marketplace API are supplied per-request via new, separate gateway headers (SOP: credentials only from headers, request-scoped, no shared state) — distinct from the four existing Reseller headers.
- Zero behavior change for the 24 existing tools and their existing four required headers.

**Non-goals** (would be scope creep on a ticket that asks for one read tool)
- No `GET /subscriptions?customerId=...` list/search tool.
- No create/update/cancel/renew tool against the Cloud Marketplace API (the "place a quantity-change order" half of the Rewst flow this ticket feeds into is not requested and not built here).
- No change to any of the 24 existing Reseller-API tools, their parameters, or their headers.
- No change to how the connector is registered on INT (same `ingrammicro` vendor; this ticket only adds optional headers a caller may send, see Risks).

### Acceptance criteria

- **AC1 (happy path)**: Given valid Cloud Marketplace credentials in the new gateway headers and a subscription id that exists, when `ingrammicro_cloud_get_subscription(subscription_id="1420038")` is called, then it returns a JSON object with `id`, `name`, `planId`, `status`, `products` (list of `mpn`/`name`/`quantity`/`unitPrice`/`currency`), `billingPeriod` (`type`/`duration`), `subscriptionPeriod` (`type`/`duration`), `renewalDate`, `customerId`.
- **AC2 (missing credentials)**: Given the Cloud Marketplace headers are not sent, when the tool is called, then it returns a structured `not_configured` error naming the missing headers, and this does **not** 401 the surrounding `/mcp` request (a request that omits only the Cloud headers but carries the four Reseller headers must still be able to call any of the other 24 tools in the same or a different call).
- **AC3 (not found)**: Given the Cloud Marketplace API responds 404 for the given id, when the tool is called, then it returns a structured `not_found` error, `retryable: false`.
- **AC4 (rate limiting)**: Given the Cloud Marketplace API responds 429, when the tool is called, then the client retries with the same backoff policy already used for the Reseller API, and if still failing after retries returns `rate_limited`, `retryable: true`.
- **AC5 (backward compatibility)**: Given a caller sends only the four existing Reseller headers (no Cloud headers at all), when any of the 24 existing tools is called, then behavior is unchanged from before this ticket (still 200, same response shape) — adding the Cloud Marketplace credential headers must not turn into a new blanket requirement on `/mcp`.
- **AC6 (multi-tenant isolation, security anchor)**: Given two concurrent requests carrying different Cloud Marketplace credentials, when both call `ingrammicro_cloud_get_subscription`, then each request's upstream call uses only its own request's credentials — no credential or token leaks across the two (verified at the request-context level, same pattern as the existing Reseller contextvar test).
- **AC7 (configurable base URL)**: Given a caller sends an override base URL header, when the tool is called, then the request goes to the overridden host/path, not a hardcoded default — because the Cloud Marketplace base URL is region/tenant-specific (see Current state) and cannot be hardcoded for all tenants.

### Open questions

- **Does "Ginko IT" need a specific region (`na`/`eu`/`stg`) baked in as the default, or is per-request override via header enough?** Not blocking: the design defaults to `na` (same convention already used for `INGRAMMICRO_BASE_URL`'s default) and lets any caller override it per request; if Ginko IT is not on `na`, whoever wires up the connector for that tenant supplies the override header. If this default is wrong for most MSPbots tenants it can be changed in config without a code change — same escape hatch the existing `INGRAMMICRO_BASE_URL` already relies on (see README "Known Gaps").
- **Will `connect.mspbots.ai`'s credential form surface the new Cloud headers as fields for existing "Ingram Micro" connections?** Not blocking implementation (see Risks & dependencies) — flagged there as a platform-side follow-up, not a reason to hold this ticket.

## Tech design

### Conclusion

Add a second, independently-credentialed HTTP client (`IngramMicroCloudClient`) and one new tool (`ingrammicro_cloud_get_subscription`) to the existing `ingrammicro-mcp` connector. The new client is wired through a second, request-scoped contextvar exactly like the existing Reseller client, but its credential headers are **optional** at the gateway-middleware level (only the one new tool needs them) — this is the one point this design deliberately diverges from the existing single-client-single-contextvar shape, and it exists specifically to satisfy AC5 (zero behavior change for the 24 existing tools).

### Where the current implementation lives

- `src/ingrammicro_mcp/api_client.py` — `IngramMicroClient`, the Reseller API client. Generic HTTP plumbing (`_request_with_retry`, `_classify`, `_raise_for_status`, timeouts, retry/backoff constants) is currently private to this module (`api_client.py:1-129`).
- `src/ingrammicro_mcp/config.py` — `Settings`, env-mode vs gateway-mode credential config for the Reseller API (`config.py:1-66`).
- `src/ingrammicro_mcp/server.py` — `_gateway_creds_var` contextvar, `get_client_from_context`, `GatewayTokenMiddleware` (hard-401s `/mcp` if any of the four Reseller headers is missing), `create_mcp_server` (registers all tool modules) (`server.py:1-159`).
- `src/ingrammicro_mcp/tools/_common.py` — `NO_TOKEN` shared error sentinel (`_common.py:1-9`).
- `src/ingrammicro_mcp/tools/renewals.py` — closest existing example of a small, read-only, two-tool module (search + get-by-id), used as the structural template for the new module.
- `tests/test_tools.py` — hardcoded `EXPECTED_TOOLS` dict asserted against `tools/list` (currently 24 entries); `tests/test_middleware.py` — 401/contextvar tests for the Reseller headers.

### Option analysis

**Where to put the shared HTTP plumbing (retry/backoff/status-classification), given the Cloud client needs the same retry-on-429/5xx behavior as the Reseller client:**

1. **Duplicate `_request_with_retry`/`_classify`/etc. inside `cloud_client.py`.** Rejected — the logic is identical (same retryable-status set, same backoff formula, same `Retry-After` handling); duplicating ~80 lines violates the "reuse first" rule and creates two places that must be kept in sync if the retry policy ever changes.
2. **Extract the vendor-agnostic parts (`_get_http_client`, `_request_with_retry`, `_RETRYABLE_STATUS`, `_MAX_RETRIES`, `_MAX_BACKOFF_SECONDS`, `_retry_delay`) into a new `src/ingrammicro_mcp/_http.py`, imported by both `api_client.py` and the new `cloud_client.py`.** Chosen. `IngramMicroError`/`_classify`/`_raise_for_status` stay in `api_client.py` as-is (its error-body shape — `{"fault": {"faultstring": ...}}` vs `{"message": ...}` — is Reseller-API-specific and already tested); the new `cloud_client.py` defines its own `IngramMicroCloudError`/`_classify_cloud`/`_raise_for_cloud_status` because the Cloud Marketplace API's error-body shape is not confirmed by any source found during research (see Decisions below) and must not be assumed identical to the Reseller API's.

**Where to put the new credential headers (middleware-mandatory vs tool-scoped optional), given `GatewayTokenMiddleware` currently 401s the whole `/mcp` endpoint if any of its four required headers is missing:**

1. **Add the Cloud headers to the same mandatory check.** Rejected outright — every one of the 24 existing tools would start requiring 4 more headers that have nothing to do with them, breaking every existing caller of this already-registered, already-in-production connector. This is exactly the kind of breaking header change the SOP (§"破坏性变更") and `mcp-track.md` 1.2 ("新加的请求头、字段，接收方要兼容「没有」") both rule out.
2. **Read the Cloud headers into a second contextvar in the same middleware pass, but do not include them in the 401 check; the new tool's own client factory returns `None` (and the tool returns a structured `not_configured` error) when they are absent.** Chosen — mirrors the existing `client_factory() -> None` / `NO_TOKEN` pattern already used for the Reseller client's own "not configured" case, just duplicated for a second, independent credential set. No new 401 path; AC5 is satisfied by construction (the mandatory check is untouched).

### Reuse & cleanup

- **Reused as-is**: `dump_json_capped`/`error_envelope` (`_json.py`) for the new tool's return value and error shape; the `ToolAnnotations(readOnlyHint=True, idempotentHint=True)` pattern from `renewals.py`; the existing `env` vs `gateway` `auth_mode` split in `config.py`, extended with a parallel set of Cloud settings rather than inventing a second config mechanism; the existing `GatewayTokenMiddleware` class (extended, not replaced).
- **New dependency**: none. `httpx` (already a dependency) covers the Cloud Marketplace API's plain REST+JSON shape; no new package needed.
- **New/changed API surface**:
  - New tool `ingrammicro_cloud_get_subscription(subscription_id: str) -> str`.
  - New `Settings` fields (gateway-mode header names + env-mode fallback values), listed in full under Data & API contract.
  - New `IngramMicroCloudClient` class (`cloud_client.py`), new `_http.py` module (extracted from `api_client.py`, no behavior change to the Reseller client — same constants, same functions, same call sites, just relocated and imported).
  - `GatewayTokenMiddleware.__call__` gains a second, non-fatal header-read block; `get_client_from_context`'s file gains a sibling `get_cloud_client_from_context`.
- **Cleanup within this change**: none needed — this is a pure addition to a connector with no dead code touched by it.
- **Follow-ups (out of scope for this ticket, listed for whoever picks them up)**: see Risks & dependencies for the `connect.mspbots.ai` credential-form gap; no other follow-up identified.

### Data & API contract

**New tool**

```
ingrammicro_cloud_get_subscription(
    subscription_id: str,   # required, e.g. "1420038"
) -> str   # JSON, same dump_json_capped(...) envelope as every other tool
```

Upstream call: `GET {cloud_base_url}/subscriptions/{subscription_id}`.

Example success response (shape per ticket + apidocs.cloud.im Products/Orders field naming):

```json
{
  "id": "1420038",
  "name": "Microsoft 365 Business Standard",
  "planId": "mpn-abc123",
  "status": "active",
  "products": [
    {"mpn": "CFQ7TTC0LH18", "name": "Microsoft 365 Business Standard", "quantity": 25, "unitPrice": 12.5, "currency": "USD"}
  ],
  "billingPeriod": {"type": "month", "duration": 1},
  "subscriptionPeriod": {"type": "year", "duration": 1},
  "renewalDate": "2027-03-01",
  "customerId": "1000001"
}
```

Error envelope (unchanged shape, reusing `_json.error_envelope`):

```json
{"error": {"code": "not_found", "message": "...", "retryable": false}}
```

**New gateway headers** (SOP: one field, one header, `X-<Vendor>-<Credential>` naming; `IngramMicroCloud` chosen to read as "Ingram Micro, Cloud Marketplace API" and stay visually distinct from the existing `X-IngramMicro-*` four):

| Header | Required | Meaning |
|---|---|---|
| `X-IngramMicroCloud-Username` | yes | Cloud Marketplace API Basic-auth username |
| `X-IngramMicroCloud-Password` | yes | Cloud Marketplace API Basic-auth password |
| `X-IngramMicroCloud-Subscription-Key` | yes | `X-Subscription-Key` value Ingram issues per Cloud Marketplace account |
| `X-IngramMicroCloud-Client-Id` | no | Forwarded as `X-Client-Id`; optional per Ingram's own docs ("for integrations with other applications") |
| `X-IngramMicroCloud-Base-Url` | no | Overrides the default `https://api.cloud.im/marketplace/na` (see Current state: base URL is region/tenant-specific) |

All five get env-mode equivalents in `Settings` (`ingrammicro_cloud_username`, `_password`, `_subscription_key`, `_client_id`, `_base_url`) for local dev, mirroring the existing four Reseller settings — same `auth_mode: env | gateway` switch, not a new one.

**Auth flow** (`IngramMicroCloudClient`, no token caching — same "re-authenticate every call" choice already made for the Reseller client, for the same reason: this is a stateless, multi-tenant service and caching a token would mean caching it per-tenant, which is exactly the shared state the SOP rules out):

1. `POST {base_url}/token`, headers `Authorization: Basic base64(username:password)` + `X-Subscription-Key: <key>` → `{"access_token": "..."}` (assumed field name `access_token`, consistent with the Reseller client's own token response and with standard OAuth2-shaped token endpoints; not independently confirmed for this specific endpoint — see Decisions).
2. `GET {base_url}/subscriptions/{id}`, headers `Authorization: Bearer <token>` + `X-Subscription-Key: <key>` [+ `X-Client-Id: <id>` if supplied].

No DB changes, no migration — this connector has no datastore.

### Key flow / sequence

```
Agent -> Gateway -> POST /mcp (tools/call ingrammicro_cloud_get_subscription)
                     headers: X-IngramMicroCloud-{Username,Password,Subscription-Key}[,Client-Id,Base-Url]
                     + the 4 existing X-IngramMicro-* headers (middleware still requires those, unrelated to this tool)
  -> GatewayTokenMiddleware: reads both header sets into two separate contextvars;
     only the original 4 are enforced (401 if missing); the 5 new ones are read best-effort
  -> ingrammicro_cloud_get_subscription tool handler
       -> get_cloud_client_from_context(settings)
            -> None if any of Username/Password/Subscription-Key missing -> tool returns NO_CLOUD_TOKEN (not_configured)
            -> else build IngramMicroCloudClient(...)
       -> client.get_subscription(subscription_id)
            -> POST {base_url}/token (Basic + X-Subscription-Key) -> bearer token
            -> GET {base_url}/subscriptions/{id} (Bearer + X-Subscription-Key[+X-Client-Id])
            -> 2xx: dump_json_capped(result)
            -> 4xx/5xx: IngramMicroCloudError -> structured error envelope (retry already applied for 429/5xx)
```

### Non-functional

- **Statelessness / multi-tenancy**: same three SOP guarantees as the rest of the connector — credentials only from headers, per-request contextvar (`set`/`finally: reset`), no caching of tokens or tenant data across requests. Verified by AC6.
- **Backward compatibility**: AC5 is the non-functional requirement doing the real work here — this ticket must not change the required-header contract of the 24 existing tools. No version bump beyond the normal one; no migration.
- **Performance**: one extra network round trip per call (token fetch, same as every Reseller call already does) — no caching, consistent with the existing per-call re-auth choice; acceptable because Rewst's own flow already does a lookup-then-order-change call pair, i.e. this is not on any new hot path.
- **Security**: Basic-auth credentials and the subscription key are only ever read from headers, never logged, never written to disk — matches `api_client.py`'s existing comment on why the shared `httpx.AsyncClient` is safe to share (no credential is ever stored on it). Response body size is capped the same way as every other tool (`dump_json_capped`).
- **Observability**: errors go through the same structured-envelope path as the rest of the connector (`code`, `message`, `retryable`); no new logging surface added or needed.

### Rollout & rollback

- **Rollout**: all five new headers are optional at the middleware level and the new tool is additive — this ships as a non-breaking change to an already-registered, already-published vendor (`mcppub publish`, not `register`). No coordination needed with the platform/gateway team to avoid breaking existing "Ingram Micro" connections.
- **Credential-form gap is a separate, non-blocking follow-up** (see Risks & dependencies) — the tool is fully usable by anyone who can set the five headers directly (e.g. a Gateway-level static header config for the Ginko IT tenant), even before any `connect.mspbots.ai` UI field exists for them.
- **Rollback**: revert the PR; no data migration, no stored state to unwind.

### Risks & dependencies

- **No breaking change to existing tools** — the design's explicit purpose (AC5, Option analysis #2) is to guarantee this; flagged as a risk here because it is the one thing that would be expensive to notice late (every one of the 24 existing tools would start 401-ing for every existing tenant).
- **`connect.mspbots.ai`'s credential form for the already-registered `ingrammicro` vendor is not automatically updated by `mcppub publish`** (only `register`, for brand-new vendors, carries `credential_fields` — confirmed via `mbp.py mcppub --help`). So this ticket ships a tool that works for any caller setting the five headers directly, but there is currently no self-service UI path on connect.mspbots.ai for a tenant to type in their Cloud Marketplace username/password/subscription key the way they can for the four Reseller fields today. **Not a reason to block this ticket** (the gap-register item only asks for the tool to exist for the migration; Ginko IT's actual credentials can be wired in at the gateway/config level without a UI), but it should be raised with whoever owns the connector's registration metadata if/when self-service onboarding for this specific capability is wanted.
- **Exact Cloud Marketplace error-body shape is unconfirmed** (see Decisions) — mitigated by a permissive, best-effort parse (checks a few common keys, falls back to raw body) rather than assuming a specific shape; if Ingram's real error bodies use a different key, the `message` field in the structured error may be less precise but the `code`/`retryable` classification (driven by HTTP status, not body shape) is unaffected.
- **No dependency on any other ticket or unreleased change.**

### Decisions made by DEV01

No one was available to ask (unattended design tick); these are the judgment calls made and why, with the rejected alternative:

- **Second contextvar + tool-scoped optional headers, not a middleware-mandatory check.** Why: the alternative breaks all 24 existing tools for all existing tenants (see Option analysis). This is the single most consequential decision in this design.
- **Default Cloud Marketplace base URL `https://api.cloud.im/marketplace/na`, override via header.** Why: the base URL is genuinely region/tenant-specific (confirmed via public integration guides) and the repo already has an identical "fully overridable base URL, picked a default, documented as unconfirmed" pattern for the Reseller API's own sandbox URL (see README "Known Gaps"); reusing that shape rather than inventing a region-enum parameter keeps the two clients consistent. Alternative considered: a `region` enum tool parameter — rejected because region is a tenant/account property, not something the calling agent should be choosing per call (same reasoning the existing code already applies to `IM-CorrelationID`: not a meaningful choice for the agent to make).
- **Separate `IngramMicroCloudError`/status-classification from the Reseller API's, not reused.** Why: the two APIs' error-body shapes are not known to be the same (no source found during research pins down the Cloud Marketplace API's error JSON shape precisely), and silently assuming they match the Reseller API's `{"fault": ...}`/`{"message": ...}` shape could silently produce wrong error messages. Shared only the HTTP-level mechanics (retry/backoff/timeout), which are not API-specific.
- **Token field assumed `access_token`.** Why: every token endpoint already documented in this repo (the Reseller API's own `GET /oauth/oauth20/token`) and the general shape described in third-party docs for this API use that field name; not independently confirmed for this exact endpoint. Flagged, not blocking — if wrong, it fails loudly (a `KeyError`/parse failure on the first real call, not a silent wrong value) and is a one-line fix.
- **`X-Client-Id` modeled as optional.** Why: Ingram's own docs describe it as needed only "for integrations with other applications" (plural/general-purpose framing), unlike the required `X-Subscription-Key`; treated the same way the existing Reseller client already treats its own optional `IM-SenderID`/`IM-ApplicationID` pair (send if configured, omit if not).

(`X-IngramMicroCloud-Username/-Password/-Subscription-Key/-Client-Id/-Base-Url`). Between
design time and this dev pass, two sibling gap-register tickets landed on `main`:
**PRD-21595** (`ingrammicro_cloud_list_subscriptions`, same Subscriptions object this ticket
needs) and **PRD-21597** (`ingrammicro_cloud_list_products`, a different object). Per
`legs/dev.md` ("technical design is dev's freedom, as long as it doesn't change user-visible
behavior") and the 2026-10-28 reuse-first rule, this ticket's implementation was adapted
rather than built from the stale plan:

- **`ingrammicro_cloud_get_subscription` was added as a new method (`get_subscription`) on
  the existing `CloudMarketplaceClient` (PRD-21595)**, not a new client class/credential
  bundle. It is the same Subscriptions object and the same account as
  `ingrammicro_cloud_list_subscriptions`, just fetched by id instead of listed — reusing it
  avoids a second, parallel credential scheme for the same data, and matches `tools/cloud.py`'s
  existing shape (two tools sharing one `cloud_client_factory`). Net effect: **no new
  credential headers for the subscription data itself** (see AC7 note below for the one
  header this ticket did add).
- **Not fixed: `CloudMarketplaceClient`'s auth scheme is flagged (by PRD-21597's own README
  note) as suspect** — PRD-21597 found Ingram's own PDF documents a Basic→token-exchange
  scheme, not this class's assumed direct-`Bearer {api_key}` scheme. This ticket inherits that
  open question (same as `list_subscriptions` already does) rather than fixing it: rewriting
  PRD-21595's already-reviewed, already-merged auth/header contract is a materially larger,
  riskier change than "add one more read method" and is out of this ticket's scope. See
  README Known Gaps for the explicit flag.
- **AC7 (configurable base URL) was not satisfiable by the as-merged `CloudMarketplaceClient`**:
  unlike the Products client, it had no per-request base-url header at all, only a single
  env-wide `INGRAMMICRO_CLOUD_BASE_URL`. Since AC7 is this ticket's own explicit, required
  acceptance criterion (the Cloud Marketplace host is tenant/region-specific, confirmed in the
  original design's "Current state" research), a small, additive, backward-compatible header
  was added: `X-IngramMicroCloud-Base-Url` (optional; absent falls back to the pre-existing env
  default, so `ingrammicro_cloud_list_subscriptions`'s behavior for existing callers is
  unchanged — verified by the updated `test_cloud_header_present_reaches_request_context_and_resets`
  and `test_two_cloud_bundles_isolated_in_the_same_request` still passing). This mirrors the
  pattern `CloudMarketplaceProductsClient` (PRD-21597) already uses for its own base URL.
