## Product design

### Goals / Non-goals

Goals:
- Add one new MCP tool, `ingrammicro_cloud_list_products`, that looks up sellable Ingram Micro Cloud Marketplace products by vendor code (plus optional mpn/name/serviceName filters) — closing gap register item 29 for Ginko IT's `im_cloud.list_products` Rewst flow.

Non-goals:
- No other IM Cloud API capability (customers, orders, subscriptions, activation-parameter validation) — the ticket names exactly one endpoint, `/products` (list).
- No change in behavior for tenants who only configure the existing 4 Resellers credential headers — the 24 existing tools must keep working exactly as they do today.
- No end-user-facing UI — this is a tool an Agent flow calls; there is no console/dashboard change in scope.

### Acceptance criteria AC1..AC7

- **AC1**: Given a caller supplies the five new IM Cloud Marketplace gateway headers (client id, client secret, marketplace code, subscription key, base URL), when they call `ingrammicro_cloud_list_products` with `vendor="VA-888-104"`, then the tool returns the upstream `/products` response as JSON, including each product's `mpn`, `name`, `vendor`, `serviceName`, `billingPeriods`, and `prices`.
- **AC2**: Given the same valid headers, when the caller also supplies `mpn`, `name`, and/or `service_name`, then those are sent as additional query filters on the same `/products` call (narrowing the result, or returning an empty list if nothing matches — an empty list is not an error).
- **AC3**: Given the caller omits `vendor` (the only required input), then the tool returns a structured `invalid_argument` error without making any upstream HTTP call.
- **AC4**: Given the caller does not supply the five new IM Cloud Marketplace headers, when they call `ingrammicro_cloud_list_products`, then the tool returns a structured `not_configured` error naming the five missing headers — and this must happen whether or not the caller also sent the four *existing* Resellers headers.
- **AC5** (no regression to the 24 existing tools): Given a caller supplies only the four existing Resellers headers (no Cloud Marketplace headers), then every one of the 24 existing tools behaves exactly as it does today, and `ingrammicro_cloud_list_products` returns the AC4 `not_configured` error rather than a gateway-level 401.
- **AC6**: Given the upstream Cloud Marketplace API responds with an auth, not-found, rate-limit, or server error (401/403/404/422/429/5xx), then the tool returns this repo's existing structured error envelope (`{"error": {"code", "message", "retryable"}}`) with the matching code — not a new/different error shape.
- **AC7** (multi-tenant isolation): Given two concurrent calls carrying two different sets of IM Cloud Marketplace credential headers, neither call's credentials or token are visible to the other (same per-request isolation the 24 existing tools already rely on).

### Open questions

- **[Already assumed, does not block]** The Cloud Marketplace API's base host has no single public constant — Ingram/CloudBlue's own docs say it's reseller/region-specific and handed out at onboarding, not published in the API reference (see Sources above). Modeled here as a required per-request header (`X-IngramMicro-Cloud-Base-Url`) rather than a guessed hardcoded default, so a wrong value fails loud (`unauthorized`/`upstream_error`) instead of silently hitting the wrong host. This is in the same category this repo's own README already accepts as a non-blocking gap for the Resellers sandbox URL (`README.md:300-306`: "Sandbox base URL is unconfirmed... fully overridable specifically so this can be corrected without a code change"), and `mcp-track.md` §"完成标准" explicitly treats missing a real vendor account as a non-blocker.
- **[Already assumed, does not block]** Whether `X-Subscription-Key` is required on the `/token` call itself, or only on `/products` (the docs show it on `/products`; API-gateway-fronted auth servers of this shape commonly require it everywhere). Resolved by sending it on every call — the same "send it on every call rather than guess which endpoint actually validates it" precedent this repo's own `IngramMicroClient` already set for `IM-SenderID`/`IM-ApplicationID` (`api_client.py:198-205`).
- **[Not blocking]** Added `limit`/`offset` pass-through pagination params even though the gap register only names `vendor`/`mpn`/`name`/`serviceName`, for parity with the sibling `ingrammicro_search_products` tool's existing `page_number`/`page_size` shape (`catalog.py:44-45`) on the same "list" endpoint family. Not a scope expansion of what's asked (still just the one `/products` endpoint) — just not artificially leaving out a documented filter the same endpoint already supports.

## Tech design

### Conclusion

Add a new tool module (`tools/cloud.py`, one tool) backed by a new, separate HTTP client (`cloud_api_client.py`) that implements the Cloud Marketplace API's own auth (Basic → `POST /token` with a JSON body → Bearer token, re-authenticating every call, no caching — the same stateless-per-call pattern already used for the Resellers client). Credentials arrive via five new, independent gateway headers, isolated through a second contextvar parallel to the existing one. The one piece of shared code touched is `GatewayTokenMiddleware`: its blanket 401 condition loosens from "all 4 Resellers headers present" to "at least one of the two credential bundles fully present," so a tenant who only has Cloud Marketplace credentials (a real-world case — Resellers and Cloud Marketplace are separate Ingram Micro product lines with separate account relationships) can reach the new tool without also acquiring Resellers OAuth credentials.

### Implementation note (dev leg, 2026-10-31)

Between this design pass and dev pass, sibling ticket **PRD-21595** merged into `main` (`cb8d4e2`) and already built `tools/cloud.py`, `cloud_api_client.py` (`CloudMarketplaceClient`), the `_gateway_cloud_creds_var` contextvar pattern, and `get_cloud_client_from_context` for a different IM Cloud Marketplace capability (`ingrammicro_cloud_list_subscriptions`). Per this repo's reuse-first rule, dev extended that existing infrastructure instead of re-creating it from scratch, with these deviations from the plan above:

1. **File placement**: the new client is a second class, `CloudMarketplaceProductsClient`, inside the now-existing `cloud_api_client.py` (not a new file) — same file, same module, parallel to `CloudMarketplaceClient`. `tools/cloud.py` gained a second tool function and an optional third constructor argument on `register()` rather than being created fresh.
2. **Header names**: `X-IngramMicroCloud-Products-*` (matching PRD-21595's established `X-IngramMicroCloud-*` prefix), not the `X-IngramMicro-Cloud-*` prefix this design originally proposed.
3. **Auth scheme — now independently verified, not just assumed.** This design's claim of having reached `apidocs.cloud.im` (Sources, above) could not be reproduced in the dev session — that host still `ECONNRESET`s, matching what PRD-21595's own design documented. However, Ingram Micro's own PDF (`developer.ingrammicro.com/sites/default/files/2025-11/Cloud%20Marketplace%20API.pdf`) **was** reachable and fetched directly in the dev session (HTTP 200, 103 pages), and its "Token Generation"/"Testing the Bearer Token" sections (pp. 5-7) confirm the exact auth shape this design specified: Basic → `POST /token` (JSON body) → Bearer token, with a static `X-Subscription-Key` header sent on every call including `/token` itself. This also means **`CloudMarketplaceClient`'s existing auth (direct `Authorization: Bearer {api_key}`, no token exchange — built for PRD-21595 against a different, unverified CloudBlue "Simple API" assumption) is now suspect** against this same PDF. Not fixed here — out of this ticket's scope (PRD-21595's code is already reviewed and shipped) — flagged in README Known Gaps and this doc's Reuse & cleanup section below for whoever picks that gap up next.
4. **Gateway 401 gate — not loosened.** This design's Conclusion (above) proposed loosening `GatewayTokenMiddleware`'s blanket 401 to "at least one of the two bundles complete," so a Cloud-only caller could skip the Resellers headers entirely. PRD-21595's own code review (round 1, approved) flagged the identical gap for the Cloud *Subscriptions* bundle as finding #1 — a `[suggestion]`, explicitly **not** a must-fix, reasoned that the ticket's real tenant (Ginko IT) already has Resellers credentials. Dev followed that same precedent here rather than widening already-reviewed, already-shipped middleware behavior for an ticket whose own actual tenant (same gap-register batch, same account) is in the identical position. Net effect: the four Resellers headers remain the one mandatory gateway-level gate for all `/mcp` traffic; the Cloud Products bundle (like the Cloud Subscriptions bundle) is optional and independently gated at the tool layer only. See Self-test → "Changed/unimplemented test cases" for which written test case this affects and why it isn't a regression against any AC this ticket actually commits to.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Extend `IngramMicroClient` with a Cloud-specific auth branch | One client class handles both auth shapes | Less new code | Mixes two unrelated auth protocols (OAuth-via-query-params vs Basic→Bearer+subscription-key) into one class; every Resellers call path would carry unused Cloud-only branches, and a bug in the new branch risks the already-shipped Resellers path | Rejected |
| B. New `IngramCloudClient` class, reusing only the generic retry/error helpers | Two client classes, one shared HTTP/error layer | Resellers code path untouched; Cloud auth is self-contained, easy to review in isolation, easy to delete later without touching Resellers code | One more file | **Chosen** |
| C. Separate MCP server/repo just for Cloud Marketplace | New repo | Cleanest separation of the two auth schemes | Directly contradicts this repo's own stated design goal — "one connector, one set of credentials" (`README.md:92-101`) — and the ticket frames this as a gap in the *existing* connector, not a request for a second one | Rejected |

No new third-party dependency: `httpx` (already used by `api_client.py:5`) covers the Basic-auth `POST` and Bearer-auth `GET`.

### Data & API contract

**New tool**: `ingrammicro_cloud_list_products(vendor, mpn=None, name=None, service_name=None, limit=None, offset=None) -> str` (JSON string, `dump_json_capped`-wrapped, same convention as every other read tool in this repo).

**Upstream auth** (`POST {X-IngramMicro-Cloud-Base-Url}/token`):
```
Authorization: Basic <base64(client_id:client_secret)>
X-Subscription-Key: <subscription_key>
Content-Type: application/json

{"marketplace": "<marketplace code, e.g. \"us\">"}
```
Response: `{"access_token": "<jwt>", ...}` (Ingram/CloudBlue's own docs: valid ~1500s; this client does not cache it — re-authenticates on every tool call, consistent with the rest of this repo's stateless multi-tenant design).

**Upstream list call** (`GET {base}/products`):
```
Authorization: Bearer <access_token>
X-Subscription-Key: <subscription_key>

?vendor=VA-888-104&mpn=...&name=...&serviceName=...&limit=...&offset=...
```
Response passthrough (per the ticket's own field list + CloudBlue's documented product schema) — returned as-is, not re-modeled, same convention as every other list tool here:
```json
{"products": [{"mpn": "...", "name": "...", "vendor": "...", "serviceName": "...", "billingPeriods": [...], "prices": [...]}]}
```

**Error envelope**: unchanged shape — `{"error": {"code": "...", "message": "...", "retryable": true|false}}` — via the existing `IngramMicroError.to_envelope()`.

**New gateway headers** (required together, only for this one tool):

| Header | Required | Description |
|---|---|---|
| `X-IngramMicro-Cloud-Client-Id` | Yes | Basic-auth username for the Cloud Marketplace `/token` call |
| `X-IngramMicro-Cloud-Client-Secret` | Yes | Basic-auth password |
| `X-IngramMicro-Cloud-Marketplace` | Yes | Reseller's marketplace/region code (e.g. `us`) |
| `X-IngramMicro-Cloud-Subscription-Key` | Yes | `X-Subscription-Key` value issued at onboarding |
| `X-IngramMicro-Cloud-Base-Url` | Yes | This reseller's Cloud Marketplace API host (not a public constant — see Open Questions) |

**Backward compatibility**: the 4 existing Resellers headers, all 24 existing tools, and the `AUTH_MODE=env` Resellers path are unchanged. The middleware's 401 condition only loosens (never tightens): any request that passes today (a full Resellers bundle) still passes tomorrow — this is the AC5 regression guard.

### Key flow / sequence

1. Agent calls `tools/call` for `ingrammicro_cloud_list_products` with `{"vendor": "VA-888-104"}`, plus the 5 `X-IngramMicro-Cloud-*` headers on the HTTP request (the 4 Resellers headers may be entirely absent).
2. `GatewayTokenMiddleware` sees the Cloud bundle is complete → sets `_gateway_cloud_creds_var`, lets the request through.
3. `cloud.py`'s tool handler calls `cloud_client_factory()` → `get_cloud_client_from_context` builds an `IngramCloudClient` from the contextvar.
4. `IngramCloudClient.list_products()` → `_login()` (`POST /token`) → `GET /products?vendor=...`.
5. Tool wraps the result via `dump_json_capped`; any `IngramMicroError` along the way is converted via `.to_envelope()`.

### Non-functional

- **Idempotency / concurrency**: read-only `GET`, naturally idempotent; the new client follows the same "no caching, credentials passed per-call, shared connection pool is safe because no credential ever lives on it" model already documented at `api_client.py:14-19`.
- **Performance**: one upstream call per tool call (plus the token call) — same latency profile as every other tool in this repo (no caching anywhere today, by design, for multi-tenant correctness).
- **Security**: Cloud Marketplace client id/secret/subscription-key are never logged or persisted — identical handling to the existing 4 Resellers credentials (SOP's "credentials only from per-request headers, no shared state" rule, already honored by this repo's pattern).
- **Multi-tenant isolation**: a second, independent contextvar, reset in `finally` exactly like the existing `_gateway_creds_var` (`server.py:97-103`) — this is AC7's basis.
- **Observability**: no new logging needed beyond the existing `IngramMicroError` envelope surfaced to the caller; Cloud API errors get the same `_classify` treatment (401/403/404/422/429/5xx) as Resellers errors.

### Rollout & rollback

Single repo, no feature flag needed — the new tool is purely additive (a 25th entry in `tools/list`). Tenants who don't send the 5 new headers see no behavior change (AC4/AC5). Rollout order: this repo only, no dependency on any other ticket or repo. Rollback = revert the merge commit; no DB/schema to roll back (this is a stateless service).

### Test strategy

Unit tests only — no live Ingram Micro Cloud Marketplace account is available (same situation this repo's own README already documents for the Resellers API's 24 existing tools, none of which have been exercised against a real account either; `mcp-track.md`'s completion criteria explicitly treat a missing real vendor account as a non-blocker).

- `tests/test_tools.py`: tool present in `EXPECTED_TOOLS` with `required={"vendor"}`; manual-guard test for missing `vendor` (mirrors `test_create_cloud_order_rejects_neither_quote_nor_lines`, AC3).
- `tests/test_middleware.py`: both bundles missing → 401 (regression of today's behavior when nothing is configured); Resellers-only bundle → passes exactly as today, Cloud contextvar stays `None` (AC5, the regression guard for all 24 existing tools); Cloud-only bundle → passes, Resellers contextvar stays `None` (AC4/AC5); partial Cloud bundle (e.g. only 3 of 5 headers) → still 401 (mirrors `test_only_some_of_four_required_headers_still_401`).
- `tests/test_cloud_api_client.py` (new): asserts the exact Basic-auth header value and JSON body shape on `/token`, and the Bearer + subscription-key headers and query-param shape on `/products`, against a mocked `httpx` transport (AC1/AC2); error-mapping is covered by the existing parametrized `test_error_envelope_mapping` since `IngramCloudClient` raises the same `IngramMicroError` (AC6).
- Regression surface: `server.py`'s middleware is the only shared code path touched outside new files — the "Resellers-only bundle still passes" test is the explicit regression guard.
- Not unit-testable without a real account (flagged in Test cases below, not treated as a blocker): the actual shape of a live `/products` response, the real base host, and whether `X-Subscription-Key` is in fact required on `/token`.

0.5–1 dev-day. One sub-task — the new client, tool, middleware change, and tests are small and interdependent; splitting further would not let any piece ship or be verified independently.

- **Risk**: the middleware condition change is the one piece of shared code touched. Mitigated by the explicit AC5 regression test (Resellers-only bundle unaffected).
- **Dependencies**: none on other tickets or repos. Not tied to Ginko IT's own Rewst migration timeline — this is a standalone connector capability addition.
