## Requirement understanding

One line: Add a tool to the Ingram Micro MCP connector that submits a change order (license-quantity increase or decrease) against an existing Ingram Micro IM Cloud subscription, so Rewst's M365-licensing purchase/remove flows can be rebuilt against it, because the connector currently only wraps the Ingram Micro Resellers API and has no IM Cloud subscription change-order capability.

Restatement: this is gap #30 from the Rewst → MSPbots migration gap register, for the Rewst account "Ginko IT". The Rewst flows this replaces call `im_cloud.generic_request` / `im_cloud.create_order` to add or remove licenses on an existing cloud subscription (e.g. M365) by posting a "change" order to the IM Cloud API's `/orders` endpoint with the subscription's new total product quantity. MSPbots' `ingrammicro-mcp` has 24 tools, all of them wrapping the Ingram Micro **Resellers** REST API (`/resellers/v6`, `/resellers/v7`); its one cloud-sounding tool, `ingrammicro_create_cloud_order`, posts to `/resellers/v7/orders` with Resellers-API `ingramPartNumber` line items — a different API, endpoint, and credential from the IM Cloud API change-order call this ticket describes. Success is: an agent can submit one change order with a subscription id, a product (mpn) and its new total quantity, and get back the IM Cloud API's order acknowledgement (id, type, status) the same way the Rewst action does today.

CloudBlue's own Simple API docs (`docs.cloudblue.com/cbc/21.0/Simple-API/how-to-use/howto/orders/`, fetched directly for this design) document a **Change Order** exactly matching the ticket's description:
  - `POST /orders` with body `{"customerId": "...", "poNumber": "...", "type": "change", "products": [{"subscriptionId": "...", "mpn": "...", "quantity": "20"}]}`.
  - Required: `customerId`, `type` ("change"), and per product item: `subscriptionId`, `mpn`, `quantity`. Optional: `poNumber`, `parameters` (product-level customization — matches the ticket's `offer_attestation`/`structured_value` example), `billingPeriod`, `subscriptionPeriod`.

  - Auth: `Authorization: Bearer {token}` plus an `X-Subscription-Key: {key}` header — the same auth shape PRD-21595 already found and used for `list_subscriptions`.
- **Not resolved by the public CloudBlue docs**: whether `billingPeriod`/`subscriptionPeriod`/`total` are actually required on Ingram's own deployment (the ticket's text says they are "taken from the subscription's own detail" and implies they're needed; the generic CloudBlue contract treats them as optional on a quantity-only change) — see Open questions / Risks.
- Direct web access to Ingram's own hosted docs (`developer.ingrammicro.com` Cloud Marketplace API PDF, `apidocs.cloud.im`) was not attempted again in this pass since PRD-21595 already recorded that this pipeline's network could not reach either URL (`ECONNRESET`/timeout); this design relies on the same independently-fetched CloudBlue Simple API contract PRD-21595 used, plus the ticket's own worked example.

## Product design

### Goals / Non-goals

**Goals**
- Add one new tool, `ingrammicro_cloud_create_change_order`, that submits a "change" order against an existing Ingram Micro IM Cloud subscription to increase or decrease a product's license quantity, so an agent can rebuild the Ginko IT `Purchase License` / `Remove License` Rewst flows against it with the same inputs (subscription id, product mpn, new total quantity) and get back the same order acknowledgement fields (`id`, `type`, `status`).
- Make explicit in the tool's parameters and docstring that the caller supplies the **new total quantity** for the product line, not a +1/-1 delta — the ticket's own text describes "quantity+1 on Purchase, -1 on Remove" as how the *caller* computes the new total before calling the API, not as two different call shapes.

**Non-goals** (not this ticket)
- Listing a customer's IM Cloud subscriptions to find the one to change — that is the separate, already-designed ticket PRD-21595 (`ingrammicro_cloud_list_subscriptions`).
- Creating a brand-new IM Cloud subscription/order (as opposed to changing the quantity on an existing one) — the gap register entry and the ticket's own example are both about changing an existing subscription.
- Polling or waiting for the change order's final (`completed`/`error`) result — IM Cloud delivers that asynchronously (same already-published product behavior as the existing `ingrammicro_create_cloud_order` Resellers tool); this tool only returns the initial acknowledgement.
- Any change to the 24 existing Resellers-API tools, including `ingrammicro_create_cloud_order`.

### Acceptance criteria AC1..ACn

- **AC1** — Given valid IM Cloud credentials and an existing subscription with a product at a known current quantity, When `ingrammicro_cloud_create_change_order` is called with that subscription's id, the product's `mpn`, and a new total quantity **greater** than the current one (an add-seats/"Purchase" change), Then the tool submits a `POST {base_url}/orders` change order and returns the upstream response (`id`, `type="change"`, `status`, and any other fields IM Cloud returns) as JSON.
- **AC2** — Given the same account and subscription, When called with a new total quantity **less than** the current one (a remove-seats/"Remove" change), Then the request and response behave identically to AC1 — there is no separate "purchase" vs "remove" mode or parameter; the direction of the change is implied entirely by whether the new total is above or below the subscription's current quantity.
- **AC3** — Given `subscription_id` or `products` (or a required field within a `products` item — `mpn`, `quantity`) is missing, or a `quantity` is not a non-negative integer, When the tool is called, Then it returns an `invalid_argument` error envelope and makes no upstream call.
- **AC4** — Given the IM Cloud API acknowledges the change order (status `submitted`/`processing`/`draft`), When the tool returns, Then the response is exactly what IM Cloud returned for that acknowledgement — the tool does not claim or imply the change has completed, and the docstring states this explicitly (the final `completed`/`error` result is delivered by IM Cloud asynchronously and is not observable from this tool, matching the already-published behavior of this connector's other cloud order tool).
- **AC5** — Given the IM Cloud credential headers (`X-IngramMicroCloud-Api-Key`, `X-IngramMicroCloud-Customer-Id`) are missing or incomplete, When any tool in this module is called, Then the response is a structured `not_configured` error naming the missing header(s), and no request reaches Ingram Micro.
- **AC6** — Given Ingram's IM Cloud API returns an error (4xx/5xx, or a network failure), When the tool is called, Then the response is a structured error envelope (`error_envelope`, same shape the Resellers tools already use) with a code, message, and `retryable` flag — never an unhandled exception or a raw stack trace.
- **AC7 (multi-tenant / BOLA)** — Given two different connected organizations (tenants) each with their own Ingram Micro Cloud account, When one organization's agent calls this tool, Then the change order is always submitted under that organization's own `customerId` — `customerId` is bound to the gateway credential for that connection, not an agent-suppliable call argument, so there is no way for a prompt or a malicious instruction to make one tenant's agent change a different tenant's subscription by passing a different id. (Same reasoning PRD-21595 already established for `list_subscriptions`'s AC7 — see Tech design → Decision 2.)
- **AC8** — Given a product line requires offer attestation (per the ticket's own Rewst example: `parameters: [{"name": "offer_attestation", "structured_value": {"attestation_accepted": true}}]`), When the caller supplies this via the optional per-product `parameters` field, Then it is included verbatim in that product's line in the request body; When omitted, Then the request is sent with no `parameters` field for that line — the tool never fabricates or defaults an attestation value.

### Open questions

- **Q1 — exact base URL, header names, and whether `billingPeriod`/`subscriptionPeriod`/`total` are actually required on Ingram's own IM Cloud deployment.** The ticket's own text says these two period objects are "taken from the subscription's own detail" (implying they matter), while the generic CloudBlue Simple API contract fetched for this design shows a minimal change order needs only `customerId`/`type`/`products[].{subscriptionId,mpn,quantity}`. **Not blocking**: this design treats `billing_period`/`subscription_period`/`total`/`po_number` as optional pass-through parameters (Decision 3) — if Ingram's real deployment requires them, the caller (or a future tool reading `ingrammicro_cloud_list_subscriptions`/`get_subscription` once that exists) already has a parameter to pass them through; no code change would be needed, only confirmation. Flagged in Risks.
- **Q2 — does `subscriptionId` belong per-product-item (as the one fetched CloudBlue example shows) or at the top level of the request (the ticket's own text flags this placement as ambiguous in Rewst's own template — it notes Rewst puts `subscriptionId` either inside `products` or at the top level, depending on the IM Cloud spec version)?** This design keeps `subscription_id` as a single required top-level *tool* parameter (matching the ticket's one-subscription-per-call workflow) but places it inside each `products[]` item in the actual request body (Decision 1), matching the one verified example. Not blocking — if Ingram's deployment expects it only at the top level instead, this is a one-line change inside `cloud_api_client.py`'s request-building code, not a change to the tool's public signature.
- **Q3 — shared with PRD-21595**: exact header names / auth exchange for Ingram's own IM Cloud deployment vs. the generic CloudBlue contract. Not blocking for the same reason PRD-21595 already recorded: the client-wrapper boundary absorbs it.

## Tech design

### Conclusion

Add a `create_change_order` method to a new, self-contained Cloud Marketplace module (new client, new tool file, new credential headers, shared HTTP plumbing extracted into a small shared module) without touching any of the 24 existing Resellers-API tools or `IngramMicroClient`. This design deliberately reuses the exact same file names, class name, constructor signature, and credential header names that the sibling ticket PRD-21595 already designed for the same IM Cloud API and the same credential material (`ingrammicro_cloud_list_subscriptions`, on branch `dev/PRD-21595`, not yet merged) — see Decision 4 and Risks for why, and what the developer/reviewer should do if both land close together.

### Where the current implementation lives

- `src/ingrammicro_mcp/api_client.py` — `IngramMicroClient` (Resellers API only); `_get_http_client`/`_request_with_retry`/`_classify`/`_STATUS_TO_CODE`/`_raise_for_status` (lines 1-40, 71-128) are generic HTTP-client plumbing with nothing Resellers-specific in them.
- `src/ingrammicro_mcp/config.py` — `Settings` (pydantic-settings), one credential set, one base URL, `auth_mode` gateway/env switch.
- `src/ingrammicro_mcp/server.py` — `GatewayTokenMiddleware` reads headers into a contextvar; `get_client_from_context` builds the client; `create_mcp_server` registers each tool module via `<module>.register(mcp, client_factory)`.
- `src/ingrammicro_mcp/tools/_common.py` — shared `NO_TOKEN` envelope constant.
- `src/ingrammicro_mcp/tools/orders.py:165-271` (`ingrammicro_create_cloud_order`) — closest existing pattern for an order-placing tool with real-money/async-result docstring warnings; used as the template for this new tool's shape and tone.

### Option analysis

1. **Add IM Cloud support to the existing `IngramMicroClient`/`Settings`** (one client, one credential set with extra optional fields) — rejected. The two APIs have unrelated auth (Resellers: OAuth2 query-param client_credentials; IM Cloud: a Bearer API key + `X-Subscription-Key`), different base URLs, and are logically different vendor products; folding them into one class would make `has_credentials`/`_login()` branch on "which API is this call for", which is more special-casing than a second small client.
2. **New client, new tool module, new credential headers, shared HTTP plumbing extracted into a small shared module** (chosen) — mirrors how this repo already separates concerns (one client = one upstream API, one tool module per capability area) and matches the shape PRD-21595 already designed for the same upstream API, minimizing eventual merge friction (Decision 4).
3. **Build the tool directly against `httpx` with no client wrapper class** — rejected, inconsistent with every other tool in this repo and would duplicate the retry/error-envelope logic `IngramMicroClient` already has.

### Data & API contract

**New tool**

```
ingrammicro_cloud_create_change_order(
    subscription_id: str,                     # required — the IM Cloud subscription to change
    products: list[dict],                     # required — [{"mpn": <required>, "quantity": <required, new TOTAL count, not a delta>, "name"?: <str>, "parameters"?: [{"name": "offer_attestation", "structured_value": {"attestation_accepted": true}}], "deals"?: {"agreements": [...], "freezePrices": false}}]
    po_number: str | None = None,
    billing_period: dict | None = None,       # {"type": ..., "duration": ...} — per ticket, "taken from the subscription's own detail" (Q1)
    subscription_period: dict | None = None,  # same shape as billing_period (Q1)
    total: dict | None = None,                # {"amount": ..., "currency": ...}
) -> str   # JSON-encoded order acknowledgement, via dump_json_capped
```

`customerId` is **not** a tool parameter (Decision 2) — it comes from the `X-IngramMicroCloud-Customer-Id` gateway header, exactly like `IM-CustomerNumber` already does for the Resellers tools and like PRD-21595 already does for `list_subscriptions`.

**Upstream call** (per the verified CloudBlue Simple API contract):

```
POST {ingrammicro_cloud_base_url}/orders
Authorization: Bearer {X-IngramMicroCloud-Api-Key}
{
  "customerId": "<from header>",
  "type": "change",
  "poNumber": "<po_number, if given>",
  "products": [{"subscriptionId": "<subscription_id>", "mpn": "...", "quantity": "...", ...}],
  "billingPeriod": {...},        # if given
  "subscriptionPeriod": {...},   # if given
  "total": {...}                 # if given
}
```

Response (per CloudBlue docs; the ticket's own text also expects a `details[]` field on completion, which this tool passes through as-is if present, not a breaking assumption either way):

```json
{"id": "...", "type": "change", "customerId": "...", "creationDate": "...", "status": "submitted"}
```

**Error envelope** (unchanged shape, reused from `_json.error_envelope`):

```json
{"error": {"code": "not_configured|unauthorized|not_found|invalid_argument|rate_limited|upstream_error", "message": "...", "retryable": false}}
```

**Backward compatibility**: fully additive. No existing header, tool signature, or response shape changes. A gateway/client that never sends the two new headers sees no behavior change in any existing tool.

### Key flow / sequence

1. Agent calls `ingrammicro_cloud_create_change_order(subscription_id="...", products=[{"mpn": "...", "quantity": <new total>}])`, having already confirmed the SKU/quantity change with a human.
2. `GatewayTokenMiddleware` has already read `X-IngramMicroCloud-Api-Key` / `X-IngramMicroCloud-Customer-Id` from the request into the Cloud contextvar (if present).
3. `tools/cloud.py` validates required fields (AC3) and calls `cloud_client_factory()`. If `None` (headers missing) → return `NO_CLOUD_TOKEN`, no upstream call (AC5).
4. `CloudMarketplaceClient.create_change_order(...)` builds `POST /orders` with `customerId` from the credential, `type="change"`, and the product line(s) carrying `subscriptionId`; sends `Authorization: Bearer <api key>`, via the shared `_request_with_retry`.
5. Success → `dump_json_capped(result)` returned as-is — the caller sees exactly the acknowledgement IM Cloud sent, including its `status` (AC1/AC2/AC4). Upstream error → `IngramMicroError.to_envelope()` (AC6).

### Non-functional

- **Multi-tenant isolation**: `customerId` is credential-bound, not agent-suppliable (AC7/Decision 2) — the one place this design actively diverges from a literal reading of the gap register's field list, for a tenant-isolation reason, same as PRD-21595's AC7.
- **Statelessness / concurrency**: `CloudMarketplaceClient` takes no shared state (api_key/customer_id passed at construction, built fresh per request via `cloud_client_factory`, same pattern as `IngramMicroClient`); the shared `httpx.AsyncClient` connection pool in `_http.py` carries no credentials.
- **Credentials**: never logged, never cached beyond the single request's contextvar lifetime — same as the existing four Resellers headers.
- **Performance**: single upstream POST per call, same retry/backoff policy (3 retries, exponential backoff capped at 20s, honors `Retry-After`) as every other tool in this repo.
- **Observability**: no new logging added; this repo has no existing per-tool logging to extend.
- **Safety**: this tool spends real money / changes real billing (it is a change order on an active paid subscription) — annotated `destructiveHint=True` and the docstring carries the same "confirm with a human before calling" instruction `ingrammicro_create_order`/`ingrammicro_create_cloud_order` already use, plus the new-total-not-delta warning (getting this backwards would over- or under-license a customer).

### Rollout & rollback

- Purely additive — ships as part of the next INT publish of `ingrammicro-mcp`'s default branch. No migration, no existing-tool behavior change, no feature flag needed: a gateway that doesn't send the two new headers never exercises the new code path beyond `cloud_client_factory()` returning `None`.
- Rollback = revert the merge commit; no data or schema to roll back (no database in this repo).

### Test strategy

- **Automated** (`tests/test_cloud_tools.py`, mocking `CloudMarketplaceClient`, following `tests/test_tools.py`'s existing pattern): add-seats call (AC1), remove-seats call using the same code path (AC2), missing required field validation (AC3), async-acknowledgement-only response shape (AC4), missing-credentials envelope (AC5), upstream-error envelope (AC6), tool-signature BOLA check (AC7), attestation `parameters` passthrough present/absent (AC8).
- **Manual, needs a real Ingram Micro Cloud Marketplace account** (not available — does not block this ticket per the vendor-mcp "no test account is not a blocker" rule): confirm the real base URL, whether `billingPeriod`/`subscriptionPeriod` are actually required by Ingram's deployment (Q1), and the real response shape against a live change order.
- **Security**: AC7 is testable without a real account — a unit test asserting the tool signature has no `customer_id`/`customerId` parameter and that `CloudMarketplaceClient.create_change_order` always sources `customerId` from `self._customer_id`, never from a call argument.

### Effort & breakdown

Small — one new client method (~40 lines, closely mirrors the shape PRD-21595 already designed for `list_subscriptions`), one new tool file (~50 lines, mirrors `orders.py`'s cloud-order tool for tone/docstring), one small refactor (`_http.py` extraction, shared with PRD-21595's need for the same thing), config/middleware wiring, README update, unit tests. Rough estimate: 0.5-1 dev day, no sub-ticket split needed.

### Risks & dependencies

- **Risk**: Ingram's own IM Cloud API deployment may use a different base URL, different header names, or may actually require `billingPeriod`/`subscriptionPeriod`/`total` that this design treats as optional (Q1). Mitigated by the client-wrapper boundary (only `cloud_api_client.py`'s internals and the tool's optional parameters are affected, not the required-parameter shape) and by building against the independently-verified CloudBlue Simple API contract rather than guessing.
- **Risk / non-blocking cross-ticket overlap**: sibling ticket PRD-21595 (branch `dev/PRD-21595`, not merged at time of writing) independently designed the same new files (`cloud_api_client.py`, `tools/cloud.py`, `_http.py`) and the same two credential headers, for the same IM Cloud API. This design deliberately copies PRD-21595's class name, constructor signature, and header names so the two are mergeable into one shared client with two methods rather than two divergent implementations (Decision 4). **Whichever of PRD-21595 / PRD-21598 reaches the review leg second should rebase onto the first's merged code and add its tool/method there, instead of re-creating the files** — this is a merge-time instruction, not a blocking dependency: each ticket is independently implementable and shippable on its own even if the other is abandoned or delayed.
- **Dependency**: none that blocks implementation. The note above is a recommendation for whoever merges second, not a requirement that PRD-21595 land first.
- **Release order**: `vendor-mcp`, single repo — no cross-repo sequencing needed (see `Track:` line in the ClickUp stub).
